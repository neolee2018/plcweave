# 第一阶段：需求、设计、编程与文档交付

2026-10-24 用户明确项目按两个部分划分，并补充第一部分需提供硬件在环测试版和正式版两份指令表。第二部分见[人工编译下载与硬件在环闭环](PART-TWO.md)。2026-10-26已有受支持FX子集的双版构建、冻结快照、两阶段交付及HIL编排入口，实际用法和边界见[两阶段工作流](../skills/plc-program-development/references/two-phase-workflow.md)；AI负责自然语言需求理解和后续文档/程序修订，不是CLI自行生成任意控制程序。

## 流程和阶段终点

用户输入需求 → 整理需求及约束 → 分配资源 → 编写设计方案和测试用例 → 冻结需求与测试 → 根据方案和用例编程 → 语法检查与回归测试 → 第一阶段交付。

第一阶段有独立的交付终点，不必等到整个项目最终验收才交付。现有 S0–S4 可承载这部分工程活动；第二阶段以 S5–S7 的厂家验证、HIL和反馈方法承载用户定义的人工下载与测试闭环。

## 第一阶段交付四类成果，程序提供两份指令表

| 文档 | 内容与职责 |
|---|---|
| 用户需求文档 | 用户需要的功能、设备、输入输出、操作流程、时序、异常响应和验收要求；用户修改需求的唯一入口，沿用 `requirements.md`。 |
| 设计方案文档 | AI根据需求整理资源分配、I/O及寄存器映射、程序结构、控制逻辑、状态转换和实现方案。 |
| 测试用例文档 | AI根据需求独立设计正常、边界、故障及恢复用例，明确输入、预期、时序、容差和覆盖关系；沿用 `test_cases.md`，先冻结再编程。 |
| 指令表程序文档与文件 | 与本版可执行程序一致的完整指令表、注释及必要说明；提供硬件在环测试版和去除测试专用接口的正式版两个指令表文件，可追溯到同版需求和设计。 |

设计方案和程序说明使用Markdown维护，需求和用例不提前生成同义JSON/YAML/CSV/PDF。两份指令表必须另提供适合目标厂家软件导入的程序文件，不能只交Markdown说明；具体方言、文件名、模板和生成入口按机型及软件版本确定并验证。FX流程中的 `source.fxil` 仍是程序源；说明和厂家导入文件由同版本源生成，避免手工维护多套程序。

两份指令表共用控制核心，第一阶段就设计好可替换的真实输入/测试注入接口、资源分配、观测点和通信参数。测试版保留注入、输入消费回声、必要的事件记录和版本身份；正式版移除测试专用注入与观测代码并接回真实I/O，保留产品需求所需的通信和诊断。不得靠任意删除程序行生成正式版。两版的差异、独立哈希和验证范围必须记录，具体检查见第二阶段规范。

四类成果（其中程序有两个版本）是客户可读成果；检查记录、独立复核记录、程序源、版本与哈希清单属于配套证据。交付仍在客户项目内建立 `delivery/<版本>/` 并打包ZIP，核验清单和压缩包，不覆盖旧版本。

## 用户只修改需求，AI维护后续成果

用户在这一阶段新增或修改传感器、按钮、LED等要求时，只需修改用户需求文档，不要求用户再逐份修改设计、用例和程序。

AI按以下顺序完成新版本：

1. 比较需求版本，识别新增、删除和修改的要求，分析资源、逻辑、时序及既有功能的影响。
2. 更新设计方案与资源分配；资源不足、行为不明确或需求互相冲突时，指出具体缺口，不擅自补成已确认要求。
3. 独立更新测试用例与需求覆盖关系，记录修改依据；完成规定复核后建立新冻结版本，保留旧冻结和旧证据。
4. 根据新方案和冻结用例修改共用控制程序，同步生成测试版、正式版两份指令表及程序说明。
5. 重新执行两版的语法检查及受影响功能和依赖的回归测试，更新相关证据和文档版本，再交付新版完整成果与ZIP。

没有需求变化的程序缺陷，仍按既有冻结预期修复程序；不能通过修改测试预期迁就实现。需求驱动修订与程序修错应明确区分。

例如需求新增“运行时LED亮，停止或故障时LED灭”，AI应检查输出资源、更新映射与控制逻辑，增加运行/停止/故障对应的用例，修改指令表并重新回归。仅写“新增LED”而未定义用途时，不能自行认定其行为。

## 交付判定和实现边界

- 四类成果及两份指令表必须对应同一需求版本，能够追溯需求、设计、用例和程序之间的关系。
- 语法检查和回归测试分别记录工具、范围及实际结果。只做语法检查不能声称功能回归通过；本地检查也不能冒充厂家编译或硬件验证。
- 未支持的指令、无法执行的用例、失败和证据缺口应如实记录；要求通过而未通过的项目不判完成。
- 需要复核的冻结、验证、重大修订和交付节点继续执行现有四名独立Agent复核规则。本文是流程定义，不是客户项目已经通过这些节点的证据。
- 当前CLI行为以README、两阶段工作流参考和实际工具为准；双程序、配套说明和打包由工具生成，需求理解、资源设计、独立测试设计及程序编写由Agent执行。跨品牌、厂家编译和硬件验证不能从本地工具检查中推断。
