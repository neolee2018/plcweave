# 第二阶段：人工编译下载与硬件在环测试闭环

2026-10-24 用户定义：接收第一阶段指令表后，由用户在厂家软件中编译、下载到PLC；告知串口后，AI编写并执行测试脚本，记录寄存器返回数据，与预期比较。程序不符合预期则迭代指令表，重新下载和测试，目标为全部规定测试通过。

本文是目标流程。现有工具的已实现范围仍以README和实际能力为准；不据此宣称跨品牌导入、双版本生成或自动测试编排已实现。第一阶段见[需求、设计、编程与文档交付](PART-ONE.md)。

## 1. 第一阶段必须准备两份程序

| 版本 | 内容 | 用途 |
|---|---|---|
| 硬件在环测试版 | 共用控制核心，加测试输入映射、受控注入、版本身份及必要观测接口。 | 用户下载到隔离测试PLC，脚本施加测试输入、采集程序输出并比较。 |
| 正式版 | 同版控制核心，连接真实输入输出，去除测试专用注入、开关和观测代码，保留产品所需通信及诊断。 | 供后续正式工程导入和现场验证。 |

两版应从共用源及明确的构建差异生成，不独立维护两套控制逻辑。资源分配须提前避开控制寄存器、保持区和机型专用区，记录接口地址、类型、单位、比例、方向、默认值及复位方式。测试模式、输入选择和物理输出路由应明确，不能假定写软元件就不会动作。

正式版去除测试接口后仍需独立做语法、资源检查与控制核心回归，确认真实I/O映射。测试版HIL通过不能自动作为正式版完整硬件通过的证据。两版分别绑定源、产物和测试版本哈希；改动控制核心后必须同步重新生成两版。

## 2. 用户负责厂家编译和下载

1. 用户选择与PLC型号兼容的软件和工程CPU，导入测试版指令表，编译并检查错误。
2. 用户完成下载，确认该版本PLC已处于RUN状态，再提供测试连接信息。
3. AI记录操作者、软件版本、编译结果、下载程序版本/哈希和RUN确认。编译错误交回AI修正导入格式或程序，不越过编译失败继续测试。

用户口述的软件名按三菱 **GX Works2**、台达 **WPLSoft / ISPSoft** 理解，具体机型支持及导入格式仍逐项目确认。官方名称依据：[三菱软件页](https://us.mitsubishielectric.com/fa/en/products/software/plc/)、[台达WPLSoft与ISPSoft说明](https://www.deltaww.com/en-US/service-support/faq/326)。不把本仓当前FX流程当作台达适配已完成。

## 3. 串口就绪后由AI执行测试

用户告知串口（如COM7）；AI结合已记录的机型、协议、波特率、数据位、校验位、停止位、从站地址及地址映射建立连接。已知参数直接复用，仅补齐缺失或变更项。编程口和测试通信口可能不同，不能仅凭端口号推断支持Modbus。

实际运行前确认隔离测试条件、连接、RUN和允许写入的测试范围。先只读核对运行版本与本轮程序及测试套件；不匹配则不注入。用户定义的是工作流，不构成对当前任何设备的实际操作授权。

AI依据第一阶段冻结的测试用例编写或更新测试脚本，脚本只负责实现初态、输入序列、采集、断言和清理，不另行定义预期。按机型和已验证接口施加受控输入，读取PLC实际寄存器和必要状态；不覆盖程序派生输出来制造通过。输入消费回声或派生量应证明PLC确已消费注入。

每个测试批次至少记录：

- 需求、测试套件、两版程序及脚本版本/哈希，下载确认、PLC身份和通信参数。
- 用例ID、初态、施加输入、原始寄存器值、类型/比例解释、时间戳、采样质量及通信错误。
- 预期与实测的比较、失败时刻和相关程序位置、结论、结束复位及资源清理结果。

原始数据和报告存入客户项目的 `evidence/`，脚本也在客户项目内留存。通信失败保留缺失和错误，不能填0。轮询无法证明的单扫描脉冲或精确时序，需PLC事件锁存/计数或外部采样；不足时保持未验证。

## 4. 比较、修复、重新下载和回归

| 结论 | 后续动作 |
|---|---|
| PASS | 记录本程序、本用例和本环境通过；继续剩余用例。 |
| PROGRAM_FAIL | 根据实际与预期差异定位控制程序问题，保持冻结预期，修复共用核心、更新两版指令表和说明，先执行本地检查与回归，再交用户重新编译和下载。 |
| TEST_INFRA_ERROR | 修复脚本、通信、映射、版本绑定或采集问题，不据此无依据修改控制程序；之后重跑。 |
| UNVERIFIED | 补足观测、环境或能力；不能按通过计数，也不能无限重试掩盖缺口。 |

迭代路径为：**AI修改程序 → 用户重新导入、编译、下载并确认RUN → AI核对新版本 → 重新测试与比较**。每次程序改变都必须重新确认实际下载版本；AI不能在用户尚未下载新版时继续把旧PLC数据归因到新版。

修复后重跑受影响用例及依赖，并在收尾执行规定的完整回归，避免修复引入新问题。新增或修改需求时回第一阶段，独立更新设计和测试预期、复核并建立新冻结；不得为了全绿放宽容差或改预期。

目标是全部规定测试通过，但不是无上限盲目循环。沿用蓝图的无改善停止规则、超时及资源清理要求；能力缺失、现场未就绪、需要用户下载或持续无改善时，保存断点、说明具体下一步，不伪造完成。需复核节点继续执行四名不同独立上下文Agent规则。

## 5. 第二阶段收尾

全部规定测试必须在最终同一程序版本和测试基线上有有效通过证据；旧版通过不能拼接成新版全通过。若存在失败、未验证、缺失或工具错误，则不宣称“全部通过”。测试版、正式版分别记录适用验证等级，软件寄存器测试不自动证明物理端子、电气、传感器或带载性能。

更新需求、设计、测试用例、双指令表及说明，附实际使用的脚本、原始返回数据、比较报告、厂家编译下载记录、复核记录和版本清单，在客户项目内生成新的 `delivery/<版本>/` 和ZIP，核验内容与哈希，保留历史版本。结束、异常和超时均释放本任务串口连接、测试注入和临时资源，不关闭用户已有软件或共享服务。
